# 0004. 운영자 권한은 허용 목록 테이블로, 백오피스 서버에서 확인한다

- 날짜: 2026-10-29
- 관련: #186, #194, ADR 0002, ADR 0003

## 상황

백오피스(`apps/admin`)는 운영자 3명이 카탈로그 · 공지를 관리하는 곳이다. 4주차 백오피스 로그인(11/5)과 공지 관리 화면이 "이 사람이 운영자인가"를 판단할 곳이 필요하다.
로그인했다는 것만으로는 운영자인지 알 수 없다. 운영자 목록을 어딘가에 두고 비교해야 한다.
AGENTS.md 규칙: secret key(`sb_secret_...`)는 클라이언트에 넣지 않고, 백오피스 쓰기는 Next 서버 쪽에서만 한다.
운영자는 3명이고 자주 바뀌지 않는다. #186 은 허용 목록이 늦으면 서버 환경변수로 대신 시작하는 것을 대비책으로 두었다.

## 선택지

| 선택지                                           | 장점                                                                            | 단점                                                                                                                          |
| ------------------------------------------------ | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 서버 환경변수에 이메일 목록                      | 테이블 · 마이그레이션 없이 바로 시작한다                                        | 바꿀 때마다 재배포한다. dev · prod 값을 따로 관리한다. 누가 운영자인지 DB 에서 볼 수 없다                                     |
| 허용 목록 테이블 + 서버에서 확인 (채택)          | 재배포 없이 SQL 로 넣고 뺀다. 앱에서는 못 읽는다. RLS 정책 · 함수가 늘지 않는다 | 확인이 서버 코드(`requireAdmin()`)에만 있다. 확인을 빠뜨린 서버 액션은 DB 가 막아 주지 않는다                                 |
| JWT 역할 claim(`app_metadata` · Auth 훅) + RLS   | DB 가 직접 막는다. 사용자 세션으로 바로 쓸 수 있다                              | 훅 · claim 설정과 테이블마다 쓰기 정책이 필요하다. 역할을 빼도 토큰이 만료될 때까지 남는다                                    |
| 허용 목록 + `is_admin()` 함수 + 운영자 쓰기 정책 | DB 가 직접 막는다                                                               | 공지 · 가챠 · 라인업 · 이미지 테이블마다 정책을 만들고 테스트해야 한다. 백오피스가 secret key 로 쓰면 쓰이지 않는 정책이 된다 |

## 결정

- 운영자 이메일은 `public.admin_allowlist(email, name, created_at)` 에 둔다. 이메일은 소문자 · 앞뒤 공백 없이만 저장한다 (check 제약).
- 이 테이블은 RLS 를 켜고 정책을 두지 않으며, anon · authenticated 권한을 회수한다. 앱은 읽지도 쓰지도 못한다.
- 백오피스 Next 서버가 secret key(Postgres 역할 `service_role`)로 허용 목록을 읽어 판단한다. 모든 서버 액션 · 라우트 핸들러는 처음에 공통 `requireAdmin()` 을 거친다.
- 비교하는 이메일은 로그인 인증이 확인한 세션 사용자의 이메일을 `lower(btrim(...))` 한 값이다. 사용자가 폼에 적은 값과 비교하지 않는다.
- 백오피스 쓰기도 secret key 로 서버에서만 한다. 그래서 `is_admin()` 함수와 운영자 쓰기 RLS 정책은 두지 않는다.
- 실제 운영자 이메일은 레포 · seed 에 넣지 않는다. dev · prod SQL Editor 에서 넣고 뺀다.
- 로그인 방식(이메일을 어떻게 확인할지)은 이 ADR 에서 정하지 않는다. 백오피스 로그인 작업(11/5)에서 정한다.

## 이유

- DB 를 쓰는 곳이 백오피스 서버 하나이고 secret key 는 RLS 를 건너뛴다. 사용자 세션으로 쓰는 곳이 없으니, 테이블마다 운영자 쓰기 정책을 만들면 쓰이지 않는 코드가 된다 (기획서 8.3).
- 환경변수보다 바꾸기 쉽고, 누가 운영자인지 DB 한 곳에서 본다. 재배포가 필요 없다.
- JWT claim 은 Auth 훅 설정과 토큰 갱신을 같이 챙겨야 한다. 운영자 3명에 비해 비용이 크다.
- secret key 를 서버에만 두는 규칙(AGENTS.md)과 그대로 맞는다.

## 알아 둘 것

- 권한 확인은 DB 가 아니라 `requireAdmin()` 에 있다. 새 서버 액션에서 이것을 빠뜨리면 운영자가 아닌 사람도 쓸 수 있다. 서버 액션을 리뷰할 때 꼭 본다.
- 허용 목록에서 빼도 열려 있는 세션은 남는다. `requireAdmin()` 이 요청마다 허용 목록을 다시 읽으면 다음 요청부터 막힌다.
- 운영자가 늘거나 역할이 나뉘거나(예: 읽기 전용), 사용자 세션으로 DB 를 쓰게 되면 이 ADR 을 대체하고 `is_admin()` · 쓰기 정책이나 JWT claim 을 다시 본다.
- 앱 사용자에게 계정이 생기면(ADR 0003 대체) authenticated 역할에 운영자 아닌 사람이 많아진다. 그때 이 테이블 · 공지 정책의 권한을 다시 확인한다.
