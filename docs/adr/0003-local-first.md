# 0003. 사용자 기록은 계정 없이 기기에만 저장한다 (로컬 우선)

- 날짜: 2026-10-22
- 관련: #147, #127, #138, #152, ADR 0002

## 상황

가챠 카탈로그(작품 · 가챠 · 라인업 · 공지)는 운영자가 쓰고 모든 사용자가 같이 읽는다. WISH / GET 기록과 폴더는 사용자마다 다르다.
기획서 6절에 "사용자 데이터를 기기에만 둘지, 계정을 만들고 서버에 둘지"가 결정 필요로 남아 있다.
레거시는 계정 없이 기기 SQLite 에만 저장했고, 기획서 2절은 "계정 없이 바로 시작, 개인 데이터는 서버로 나가지 않는다"를 핵심 가치로 둔다.
1.0 은 11/8 출시이고 개발에 쓸 수 있는 시간은 3주다. Supabase 스키마 · RLS 는 소정이 주말 3시간씩 맡는다.
2주차에 로컬 items · folders CRUD(#138)를 붙이므로 그 전에 기록을 어디에 둘지 정한다.

## 선택지

| 선택지             | 장점                                                                               | 단점                                                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 계정 + 서버 저장   | 기기를 바꿔도 기록이 남는다. 백업 · 동기화 · 1.1 AI 인식이 단순해진다 (기획서 6절) | 로그인 · 가입 화면, 사용자별 RLS, 계정 삭제 기능이 1.0 에 들어온다. 설치 직후 바로 못 쓴다. 오프라인에서 기록이 막힌다 |
| 로컬 우선 (채택)   | 설치 직후 바로 쓴다. 오프라인에서도 기록된다. 기록이 서버로 나가지 않는다          | 앱을 지우거나 기기를 바꾸면 기록이 사라진다. 여러 기기에서 같이 못 본다                                                |
| 로컬 + 나중 동기화 | 오프라인 · 기기 변경을 모두 해결한다                                               | 지금부터 동기화 설계(충돌 해결, 삭제 표시, 변경 추적)가 필요하다. 결국 계정도 필요하다. 3주 안에 끝낼 수 없다          |

## 결정

- WISH / GET 기록(items)과 폴더(folders)는 기기의 로컬 DB(drizzle + expo-sqlite, `apps/mobile/lib/db`)에만 저장한다. 회원가입 · 로그인은 1.0 에 넣지 않는다.
- 원격 카탈로그와 로컬 기록은 `gacha_id` 하나로만 이어진다. 로컬 `items` 는 가챠 정보(이름 · 이미지 · 가격)를 복사해 두지 않고 `gacha_id` 로만 가리키며, 화면에 보일 때 카탈로그 쪽(Supabase)에서 가챠 정보를 가져와 합친다 (기획서 7절). 두 DB 사이에 외래 키는 없다. 기록 자체의 이름 · 사진 · 메모는 로컬 `items` 에 있다.
- 데이터 접근은 저장소 인터페이스로 나눈다 (ADR 0002 의 경계를 따른다).

| 저장소                                               | 인터페이스 (`packages/core`)           | 구현                                                                                      |
| ---------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------- |
| `gacha` (원격 카탈로그, 읽기 전용)                   | `repositories/gacha.ts`                | core: 메모리(목) → Supabase                                                               |
| `items` · `folders` (로컬 기록, `LocalRepositories`) | `repositories/items.ts` · `folders.ts` | 앱: `lib/db/localRepositories.ts` (drizzle). core 에는 테스트 · 웹 미리보기용 메모리 구현 |

- 앱은 `lib/repositories.ts` 에서 둘을 묶어 `CoreProvider` 에 넘긴다. 백오피스의 저장소 묶음(`apps/admin/lib/repositories.ts`)에는 `gacha` 만 있다 (`Repositories` 에서 로컬 쪽은 `Partial`). 화면은 core 의 훅만 쓰고, 기록이 기기에 있는지 서버에 있는지 모른다.
- 나중에 서버로 옮길 수 있게 로컬 스키마를 서버 테이블과 같은 모양으로 둔다: id 는 UUID 텍스트, 시각은 ISO 8601 UTC, 기본 폴더는 id 가 아니라 `is_default` 로 찾는다. 다만 로컬 `items.gacha_id` 는 text, 서버 `gacha.id` 는 bigint 라서 서버로 옮길 때 형 변환이 필요하다.
- 기록(items · folders)은 서버에 저장하지 않는다. 서버로 나가는 것은 익명 기기 UUID 를 붙인 조회 로그 · 가챠 등록 요청 · 문의(feedback, 첨부 사진 포함), 오류 수집(Sentry) 이벤트, 1.1 사진 인식 때 보내는 사진이다.

## 이유

- 기획서의 핵심 가치("계정 없이 바로 시작")와 맞고, 레거시 사용자의 흐름도 그대로다.
- 3주 안에 계정을 넣으면 로그인 화면 · 사용자별 RLS · 계정 삭제(스토어 심사 요건)까지 1.0 범위가 늘어난다.
- 동기화는 충돌 해결과 삭제 표시까지 설계해야 해서, 지금 일부만 넣으면 쓰지 않는 코드가 된다 (기획서 8.3 "쓰지 않는 코드는 오해와 버그의 원인").
- `gacha_id` 하나로만 잇으면 카탈로그의 이름 · 이미지 · 가격이 바뀌어도 로컬 기록을 고칠 필요가 없다. 기록 테이블이 서버 쪽 사용자 테이블로 그대로 옮기기 쉬운 모양이 된다 (기획서 부록 A.3).
- 저장소 인터페이스로 나누면 나중에 계정 · 동기화를 붙일 때 `lib/repositories.ts` 의 구현만 바꾸고 화면 · 훅은 그대로 둔다. 같은 인터페이스의 메모리 구현으로 훅을 기기 없이 테스트한다.

## 잃는 것

- 앱을 지우거나 기기를 바꾸면 기록 · 폴더와 앱 안에 복사해 둔 사진(3주차 예정)이 모두 사라진다. 기획서 부록 A.3 도 이것을 "현재 구조의 가장 큰 위험"으로 적었다.
- 한 사람이 여러 기기에서 같은 기록을 볼 수 없다.
- **백업 계획: 미정.** 1.0 · 1.1 일정에 사용자 기록 백업 · 내보내기 작업은 없다. 기획서 부록 A.3(재개발 전 로드맵, 참고용)에 계정 · 동기화 단계와 백업이 유료 기능 후보라는 메모가 있을 뿐, 언제 어떻게 할지는 정하지 않았다.

## 알아 둘 것

- 계정 · 동기화 · 백업을 넣기로 하면 이 ADR 을 대체하는 새 ADR 을 쓰고, ADR 0002 의 "로컬 DB 를 core 로 옮길지"도 같이 본다.
